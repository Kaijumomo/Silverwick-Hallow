CONNECTION BEHAVIOR
Development mode or the VITE_FIREBASE_ENVIRONMENT=development marker always
requires all seven exact public identifiers in DEVELOPMENT_FIREBASE_CONFIG.
Mixed production configuration, missing fields, extra SDK options, redirected
database URLs and browser-saved configuration fail before SDK initialization
or cache reuse. No environment-variable or localStorage bypass was introduced.
The former unconditional throw is replaced by this configuration guard.

The approved app initializes lazily as silverwick-hollow-development, separated
from the default SDK app and its persisted Auth state. The cache identity includes
the development context and all seven SDK fields; Auth cannot be reused solely
because projectId and databaseURL match. A partially failed initialization does
not replace a valid cached set of app/database/auth instances. Unmarked production
initialization continues using the default app and existing configuration flow.

No new login, backend, self-enrollment or authorization model is introduced.
The existing anonymous sign-in and authoritative game-state flow remain in use.
Configuration acceptance does not grant data access: deployed Rules still require
an administrator-approved anonymous UID, role, future expiry and, for players,
the exact game/session grant plus the existing roster/join permissions.
The named development app uses a separate Firebase Auth persistence namespace;
do not expect a UID from an old default-app browser session to transfer.
